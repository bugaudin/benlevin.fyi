ikite.fyi

2023 – Present

Case study · sole engineer & operator

Live at ikite.fyi

Israeli Mediterranean wind & meteorological monitoring platform

Go · MySQL · OCI · systemd · Docker · ApexCharts · Telegram API

Kitesurfers on the Israeli coast decide whether to drive an hour based on wind that changes in twenty minutes. Public sources are scattered, slow, and mostly Hebrew PDFs. I built the thing I wanted to exist, then kept it running for three years.

Architecture

4 external sources → scheduled Go collectors (systemd timers) → MySQL time-series → Go HTTP API → ApexCharts UI + Telegram alerting

Collectors poll Windguru, the IMS Envista API, and local Israeli station feeds on independent schedules, so one flaky upstream cannot stall the others. A second pipeline ingests daily forecasts: openWRF PDF parsing, OpenSkiron 4 km GRIB, Open-Meteo models, and a Hebrew AI forecast report that is machine-translated to English on ingest. Everything runs on a single Oracle Cloud instance under systemd, with the binary and its assets deployed as one artifact.

Why I rewrote it from PHP to Go

The 2023 PHP version worked, but every collector was a separate cron-invoked process paying full interpreter startup, and concurrent polling meant either blocking or process sprawl. Go gave me goroutine-per-collector concurrency in one supervised process, a single static binary to deploy, and a memory profile that fits comfortably inside a free-tier VM. The 2026 rewrite is the version running today.

  • ~15 MB resident memory for the whole service, versus a PHP-FPM pool
  • Sub-millisecond API responses on cached station reads
  • One artifact to deploy — static binary plus embedded assets, no runtime to keep patched
  • Zero unplanned outages attributable to collector concurrency since the rewrite
What running it for three years taught me

Upstream feeds fail in undignified ways — a station returns yesterday's reading with today's timestamp, a PDF layout shifts, a GRIB file arrives truncated. Most of the engineering is not the happy path; it is staleness detection, per-source backoff, and alerting that distinguishes "no wind" from "no data". The Telegram threshold alerts had to learn the difference the hard way.
